# Retired Features

Civitas has gone through several rewrites on the road to market readiness.
This page catalogs the components that have been replaced or hidden, so
historical context isn't lost and so a future contributor can tell at a
glance whether a file they're reading is live code or vestigial.

A few of these still ship as source files because their replacements
borrow types or helpers from them; a few still exist as routes under a
feature flag. None of them are reachable from the live navigation.

Status legend:

- **Removed from UI, code present** — file exists, no entry point in the
  active navigation. Safe to delete only after auditing imports.
- **Hidden behind feature flag** — code lives in a live page, gated by a
  `false` constant.
- **Replaced, source deleted** — only mentioned here for historical
  searchability.

## Matching algorithm v1 (`rfp-matching.ts`)

**Status:** Removed from UI; types still imported by retired pages.

**Replaced by:** [`matching-v2.ts`](../front_end/src/lib/matching-v2.ts).
See [Matching-Algorithm-v2](Matching-Algorithm-v2).

The original 1,300-line client-side scorer ran in the browser, used
synonym-Jaccard similarity across 10 hand-weighted categories, and
treated empty RFP fields as zero. It powered the legacy `/dashboard`
view.

v2 is server-side, source-aware (an empty PlanetBids `licenses_required`
is "unknown" not "missing"), uses pgvector cosine similarity on
Voyage-3-large embeddings for specialty / capability matching, runs a
prime + sub-on-prime track in parallel, computes win probability
separately from score via an incumbent state machine, and emits a
per-category citation (RFP phrase + profile claim) with every result.

The v1 file is still imported in three places:

- `app/dashboard/page.tsx` and `app/dashboard/rfp/[id]/page.tsx` (the
  retired dashboard, see below).
- `app/matches/[rfpId]/page.tsx` and `components/PrefetchEvents.tsx`
  import only the `CompanyProfile` / `RFP` *types* — the matching
  functions themselves are not called.

The synonym map and canonicalization tables in `rfp-matching.ts` also
inform helpers reused by v2 (`profile-naics.ts`, `naics-similarity.ts`).

Historical detail of the algorithm: [Matching-Algorithm](Matching-Algorithm).

## Legacy `/dashboard` view (`app/dashboard/page.tsx`)

**Status:** Removed from UI navigation; route still resolves.

**Replaced by:** [`/matches`](../front_end/src/app/matches/page.tsx) plus
[`/home`](../front_end/src/app/home/page.tsx) for the overview surface.

The original dashboard was a 2,700-line single-page React app with 12
filter chip groups, client-side scoring against every RFP in the
catalog, and proposal / Plan-of-Execution generation panels inline on
the detail view. The new flow splits this into:

- `/home` — pipeline counters (saved / in_progress / bid_submitted /
  won / lost / no_bid), upcoming deadlines, mini calendar.
- `/matches` — pre-scored list backed by `match_state.cached_*` columns,
  with the v2 filter chips driven by Postgres rather than client-side
  filtering of S3 reads.
- `/matches/[rfpId]` — v2 detail with Prime + Sub track tabs and
  per-category citations.
- `/tracker` — bidding-pipeline tracker with full FullCalendar view and
  per-RFP task lists.

The dashboard file itself sets `const SHOW_AI_GENERATION = false` near
the top, hiding the proposal / POE buttons even on the legacy route.

## Legacy profile editor (`app/profile/page.tsx`, `app/profile-setup/page.tsx`)

**Status:** Removed from UI navigation; routes still resolve.

**Replaced by:** [`/profile/v2`](../front_end/src/app/profile/v2/page.tsx).
The header navigation links the "Profile" tab directly to `/profile/v2`.

The old `/profile` was a 1,400-line monolithic editor that wrote the
profile shape from the v1 dashboard (flat string arrays for everything,
no provenance, no claim review). `/profile-setup` was its first-time
companion populated from the bulk-upload extractor.

The v2 editor renders one `EditableSection` per profile dimension, and
each section reuses the same widget the onboarding wizard uses
(`StepIdentity`, `StepSpecialties`, …) so there's a single source of
truth for the UI of each field. Each section auto-saves on change;
provenance from accepted claims is shown inline.

## AI Proposal generation

**Status:** Hidden behind `SHOW_AI_GENERATION = false`; backend route
remains for emergency re-enable; no live UI calls it.

**Original surface:** "Generate Proposal" button on the legacy RFP
detail page (`/dashboard/rfp/[id]`) and the legacy dashboard.

**Replaced by:** Nothing user-facing for now. Decision is intentional —
launch focus is on the discovery / matching loop, not on autogenerated
written documents.

The backend pipeline still lives at:

- [`/api/generate-proposal`](../front_end/src/app/api/generate-proposal/route.ts)
- [`/api/user/generated-proposal`](../front_end/src/app/api/user/generated-proposal/route.ts)
  for retrieval
- `generated_documents` Postgres table for persistence

Re-enabling is a one-line flag flip in `app/dashboard/page.tsx`. Long
term the v2 detail page (`/matches/[rfpId]`) would need to grow the
button surface; the current detail page intentionally has no proposal
button at all.

## Legacy `/upload` bulk extractor

**Status:** Live, but transitional. The post-onboarding hand-off still
drops the user here, and the v2 `/profile/v2` page links to it.

**Replaced by:** [`/contracts`](../front_end/src/app/contracts/page.tsx)
+ per-doc claim review at `/contracts/[id]/review`. The v2 flow
classifies each upload (`proposal` / `executed_contract` /
`capability_statement` / `license_doc` / `rfp_solicitation` / `other`),
extracts targeted claims, and surfaces them for accept / reject before
any profile row is written.

The `/upload` route still accepts multi-file drag-and-drop and runs the
older "extract everything in one LLM call, write to flat profile
arrays" path. Kept live because the v2 review flow is one-doc-at-a-time
and the onboarding hand-off needs a multi-file batch entry point until
the v2 flow grows one.

## Webscraping v1 (top-level `webscraping/*.py`)

**Status:** Source files present; not invoked by the Lambda or by any
production code path.

**Replaced by:** [`webscraping/v2/`](../webscraping/v2/) — see
[`webscraping/v2/README.md`](../webscraping/v2/README.md) and
[`webscraping/v2/COVERAGE.md`](../webscraping/v2/COVERAGE.md).

Files still on disk but retired:

- `webscraping/cal_eprocure.py` — original Cal eProcure scraper. Direct
  Playwright invocations against the portal with no orchestrator and no
  S3 manifest pattern. v2 ships the same source under
  `webscraping/v2/scrapers/caleprocure.py` inside the runner /
  orchestrator pipeline.
- `webscraping/extract_attachments.py` — standalone PDF download +
  PyMuPDF extraction script. v2 folds this into
  `webscraping/v2/pipeline/enrich.py`, which adds PII redaction, SSRF
  protection, Claude Haiku enrichment with prompt caching, and writes
  results back to the same S3 manifest.
- `webscraping/cal_eprocure_store.py`, `webscraping/RFP_Parsing.py` —
  one-shot utility scripts from the early CSV-output era; replaced by
  the manifest writer in v2.
- The committed CSV / JSON artifacts (`all_events_detailed.csv`,
  `all_events_detailed.json`, `attachment_extractions.json`) are
  historical exports of the v1 pipeline. Not regenerated.

## AWS SES outbound

**Status:** Removed for outbound delivery; bounce / complaint webhook
retained for messages sent during the SES era.

**Replaced by:** Resend, via [`lib/email.ts`](../front_end/src/lib/email.ts).
All signup verification, password reset, and daily-roundup mail goes
through Resend on the `civitas-ai.net` domain.

The SES bounce / complaint webhook at
[`/api/email/ses-events`](../front_end/src/app/api/email/ses-events/route.ts)
is still mounted and still verifies SNS signatures via
[`lib/sns-verify.ts`](../front_end/src/lib/sns-verify.ts), because old
messages we sent through SES can still bounce months later. No new
mail goes out through SES.

The SES production-access re-submission item in older memory notes is
moot: SES is no longer the outbound provider.

## Legacy 48-hour scrape schedule

**Status:** Replaced.

**Now:** EventBridge fires
[`webscraping/v2/deploy/template.yaml`](../webscraping/v2/deploy/template.yaml)
on `rate(12 hours)` with `{"mode":"all"}`, plus a daily
exploration / onboarding rule at `cron(0 13 * * ? *)`. 

The daily-roundup Lambda runs on `rate(1 hour)` so it can fire at each
user's local 7am for any timezone.

## S3-as-database for user profiles

**Status:** Replaced.

**Replaced by:** Postgres on RDS. Profile, contracts, claims, match
state, generated documents, and the RFP cache all live in Drizzle-managed
tables; see [Architecture-v2 § 4](Architecture-v2.md#4-postgres-schema)
and [`db/schema.ts`](../front_end/src/db/schema.ts).

A small number of user-scoped values still live in the per-user S3 JSON
blob (`users/{username}.json`) — generated POE / proposal markdown and
match-feedback snapshots, via
[`lib/user-data.ts`](../front_end/src/lib/user-data.ts) and
[`lib/rfp-status.ts`](../front_end/src/lib/rfp-status.ts). Migrating
these into the existing `generated_documents` and `match_state` tables
is tracked in [TODO](TODO).

## Agentic scrapers for LA City + SF City

**Status:** Disabled in the registry.

The two agentic scrapers (`webscraping/v2/scrapers/agentic.py`) targeted
`labavn.org` (LA City) and an SF City procurement URL. LA fails DNS
resolution from the Lambda environment; the SF URL returns 404. Both
sites are flagged in the registry; the runner skips them. Re-onboard
via `{"mode":"discover"}` + `{"mode":"onboard"}` when working endpoints
are confirmed.
